## Ordered experiments (run in this sequence)

### 1. **Test DCOMP descriptor full-range init** (highest priority)

BSP writes 0x1114-0x114c (15 entries, all values 0) — a "table init to zero" pattern. Mesa doesn't write any of these. Hypothesis: CNA's DCOMP unit needs its descriptor table EXPLICITLY zeroed via regcmd, not just left at default.

Implementation: extend the BSP-inject block to add 15 regcmd entries. Need 15 slots — we currently use 4, 5, 126, 127, 128. To get 15 more, we need to:
- Option A: append after mesa's last entry (positions 133..147) and bump `task->regcmd_count` and the AMOUNTS write by 15. BUT entries at positions 133+ would fire AFTER OP_ENABLEs at 129-132. Late. Probably no effect.
- Option B (correct): **shift mesa's OP_ENABLE entries (129-132) forward** by 15 slots to positions 144-147, and inject 15 DCOMP entries at positions 129-143.

Code skeleton:
```c
if ((int)task->regcmd_count >= 133) {
    /* Save mesa's 4 OP_ENABLE entries */
    u32 op_w0[4], op_w1[4];
    for (i = 0; i < 4; i++) {
        op_w0[i] = p[(129+i)*2];
        op_w1[i] = p[(129+i)*2 + 1];
    }
    /* Inject 15 DCOMP descriptor zeroing entries at 129..143 */
    static const u32 dcomp_offsets[] = {
        0x1114, 0x1118, 0x111c, 0x1120, 0x1124, 0x1128, 0x112c,
        0x1130, 0x1134, 0x1138, 0x113c, 0x1140, 0x1144, 0x1148, 0x114c
    };
    for (i = 0; i < 15; i++) {
        p[(129+i)*2] = dcomp_offsets[i];   /* val=0, off=dcomp_offsets[i] */
        p[(129+i)*2 + 1] = 0x02010000;     /* routing=0x02 (CNA) */
    }
    /* Put OP_ENABLEs at 144..147 */
    for (i = 0; i < 4; i++) {
        p[(144+i)*2] = op_w0[i];
        p[(144+i)*2 + 1] = op_w1[i];
    }
    /* Bump regcmd_count so AMOUNTS register write reflects the new count.
     * task is &job->tasks[next-1] — we can mutate it for this submit. */
    task->regcmd_count += 15;
}
```

Expected outcome:
- If CNA enters EXECUTER → DCOMP table init was the missing piece. Output may still be wrong (mesa's weights might be wrong) but CNA runs.
- If still no EXECUTER → tables aren't the gate. Move to step 2.

### 3. **CNA S_STATUS bit decode** (only if 1+2 fail)

Read the TRM doc more carefully. CNA_S_STATUS field layout — what are bits 2, 17 (rocket sees) vs bits 3, 16 (BSP sees)?

Check `rocket_registers.h` for `CNA_S_STATUS_*` field defs. The bit names will reveal what state each sub-unit is in.

Probable interpretations:
- bit 16 = EXECUTER (we know this from CNA_S_POINTER defs — same field name)
- bit 17 = some "wait" / "stalled" state
- bit 2 vs bit 3 = different "ready" levels

Once the bit names are known, we can target the missing state directly.

### 4. **Trivial-conv test** (if 1+2+3 yield nothing)

The current test is mesa's `conv2d.tflite` — 80×80×16 input → 40×40×128 output, 5×5 kernel. Possibly an edge case for CNA. Build/run a SIMPLER conv (1×1 kernel, tiny tensor) through mesa Teflon. If THAT runs, the bug is mesa-conv2d-specific.

### 5. **Power+clock state diff** (if regcmd content really is irrelevant)

The `RKNPU_DUMP_BEFORE_OPEN` block (already in BSP code) captures PMU PWR_STATUS, NOC_AUTO, BUS_IDLE_ST, CRU clock states. Compare BSP-success vs rocket-broken at the cycle right before OP_EN.

Differences in any of these = HW state mismatch.

## What NOT to do

- Don't try `wmb()` + memremap regcmd patching (crashed board on 2026-05-18 — see [[rocket-pc-unblock-2026-05-18]]).
- Don't write `0xe` to CNA_S_POINTER from CPU (blocks PC broadcast).
- Don't write `0x2` (PP_EN bit 1) alone to any S_POINTER (blocks PC broadcast).
- Don't enable runtime PM autosuspend on NPU (CLAUDE.md notes warn).
